# 6. 读路径分层架构

## 6.1 读路径分层架构概览

读路径分层架构是 LSM-Tree 存储引擎查询数据的核心机制。它定义了数据查询的顺序和版本可见性规则。

**核心查询顺序：**
```
用户查询 Key
    ↓
MemTable (内存，最新)
    ↓
SSTable L0_003.sst (最新)
    ↓
SSTable L0_002.sst (较旧)
    ↓
SSTable L0_001.sst (最旧)
    ↓
返回结果
```

## 6.2 为什么查询要按 MemTable → SSTable 的顺序？

**答案：因为数据是按时间顺序从新到旧分布的。**

**写入流程的时间线：**
```
用户请求 Put(A=1)
    ↓
1. 写入 WAL (持久化)
    ↓
2. 写入 MemTable (内存，最新)
    ↓
3. MemTable 满了 → Flush
    ↓
4. 生成 SSTable L0_001.sst (磁盘，较旧)
```

**关键理解点：**
- **MemTable**：驻留在内存，包含最新的写入操作
- **SSTable**：持久化在磁盘，包含已 Flush 的历史数据
- **时间维度**：MemTable 中的数据一定比任何 SSTable 中的数据更新

**查询流程图解：**
```
用户查询 Key=5
    ↓
1. 先查 MemTable（内存，最快）
   - 找到 → 立即返回（这是最新版本）
   - 未找到 → 继续
    ↓
2. 再查 SSTable（磁盘，较慢）
   - 按文件生成时间从新到旧遍历
   - 找到 → 立即返回
   - 遍历完所有 SSTable → 返回"不存在"
```

**代码实现示例：**
```cpp
std::optional<std::string> KVStore::get(const std::string& key) {
    // 1. 先查 MemTable
    auto mem_result = memtable_->search(key);
    if (mem_result.has_value()) {
        return mem_result;  // 找到就返回，不继续查 SSTable
    }
    
    // 2. 再查 SSTable（从新到旧）
    for (auto it = sstables_.rbegin(); it != sstables_.rend(); ++it) {
        auto sst_result = (*it)->get(key);
        if (sst_result.has_value()) {
            return sst_result;  // 找到就返回
        }
    }
    
    // 3. 都没找到
    return std::nullopt;
}
```

## 6.3 为什么从新到旧遍历 SSTable？

**答案：因为同一个 Key 可能在多个 SSTable 中存在，我们需要返回最新版本。**

**场景示例：**
```
时间线：
T1: Put(A=1) → Flush → L0_001.sst (A=1)
T2: Put(A=2) → Flush → L0_002.sst (A=2)
T3: Put(A=3) → Flush → L0_003.sst (A=3)
T4: Put(A=4) → 当前在 MemTable 中
```

**查询 Key=A 时的遍历顺序：**
```
1. MemTable: 找到 A=4 → 返回 4（最新！）
   如果 MemTable 中没有：
2. L0_003.sst: 找到 A=3 → 返回 3
   如果 L0_003 中没有：
3. L0_002.sst: 找到 A=2 → 返回 2
   如果 L0_002 中没有：
4. L0_001.sst: 找到 A=1 → 返回 1
```

**为什么不能从旧到新？**
- 如果从旧到新遍历，你需要遍历完所有 SSTable 才能确定哪个是最新版本
- 效率极低，违背了"找到即返回"的优化原则

## 6.4 版本可见性：同一个 Key 在多个层级存在时，应该返回哪个版本？

**答案：返回第一个找到的版本（即最新版本）。**

**核心原则：**
- **找到即返回**：一旦在某个层级找到 Key，立即返回，不再继续查找
- **层级优先级**：MemTable > 新 SSTable > 旧 SSTable
- **时间单调性**：查询结果的时间戳（隐含）是单调递减的

**多版本场景分析：**
```
假设有多个版本的数据：
- MemTable: A=4 (最新)
- L0_003.sst: A=3
- L0_002.sst: A=2
- L0_001.sst: A=1 (最旧)

查询 Key=A:
1. MemTable 找到 A=4 → 返回 4，停止查询
```

## 6.5 Tombstone（删除标记）机制

### 6.5.1 为什么需要 Tombstone？

**问题背景：**
- SSTable 是不可变的（Immutable），一旦生成就不能修改
- 如果 Key 在 L0_001.sst 中存在，用户执行 Delete，我们不能修改 L0_001.sst
- 直接物理删除会导致查询时无法判断"Key 是否被删除过"

**解决方案：**
- Delete 操作写入一个特殊的"删除标记"（Tombstone）
- Tombstone 通过 ValueType 枚举来标识，与普通值区分
- 查询时遇到 Tombstone，返回"不存在"并停止查找

### 6.5.2 Tombstone 的语义与实现

**ValueType 枚举定义：**
```cpp
enum class ValueType : uint8_t {
    NORMAL = 0,      // 普通值
    TOMBSTONE = 1    // 删除标记
};

struct Value {
    std::string data;
    ValueType type = ValueType::NORMAL;
    
    bool is_tombstone() const { return type == ValueType::TOMBSTONE; }
    
    static Value normal(const std::string& d) { return Value{d, ValueType::NORMAL}; }
    static Value tombstone() { return Value{"", ValueType::TOMBSTONE}; }
};
```

**为什么使用 ValueType 枚举而非特殊字符串？**
- 使用字符串常量（如 `"__tombstone__"`）会导致冲突：用户无法存储这个值
- ValueType 枚举完全避免了这个问题，用户可以存储任意字符串

**Delete 操作实现：**
```cpp
bool KVStore::del(int key) {
    // 1. 写入 WAL（持久化）
    LogRecord record{LogType::kDelete, FormatKey(key), Value::tombstone()};
    append_wal(record);
    
    // 2. 写入 MemTable（插入 Tombstone，而非物理删除）
    memtable_.insert(key, Value::tombstone());
    return true;
}
```

**查询时的处理：**
```cpp
std::optional<std::string> KVStore::get(int key) {
    // 查 MemTable
    auto result = memtable_.search(key);
    if (result.has_value()) {
        if (result->is_tombstone()) {
            return std::nullopt;  // 遇到 Tombstone，返回"不存在"
        }
        return result->data;
    }
    
    // 查 SSTable（从新到旧）
    for (auto it = sstable_readers_.rbegin(); it != sstable_readers_.rend(); ++it) {
        auto sst_result = (*it)->Get(key);
        if (sst_result.has_value()) {
            if (sst_result->is_tombstone()) {
                return std::nullopt;  // 遇到 Tombstone，停止查找
            }
            return sst_result->data;
        }
    }
    
    return std::nullopt;
}
```

### 6.5.3 Tombstone 场景分析

**场景1：删除后查询**
```
时间线：
T1: Put(A=1) → Flush → L0_001.sst (A=1, NORMAL)
T2: Delete(A) → 写入 Tombstone → Flush → L0_002.sst (A="", TOMBSTONE)

查询 Key=A:
1. MemTable: 未找到
2. L0_002.sst: 找到 A (TOMBSTONE) → 返回"不存在" ✅
   （遇到 Tombstone 就停止，不继续查 L0_001）
```

**场景2：删除后重新写入**
```
时间线：
T1: Put(A=1) → Flush → L0_001.sst (A=1, NORMAL)
T2: Delete(A) → 写入 Tombstone → Flush → L0_002.sst (A="", TOMBSTONE)
T3: Put(A=2) → 当前在 MemTable (A=2, NORMAL)

查询 Key=A:
1. MemTable: 找到 A=2 (NORMAL) → 返回 2 ✅
   （即使 L0_002 中有 Tombstone，也不会查到，因为 MemTable 优先）
```

**场景3：存储特殊字符串 "__tombstone__"**
```
时间线：
T1: Put(A="__tombstone__") → 当前在 MemTable (A="__tombstone__", NORMAL)

查询 Key=A:
1. MemTable: 找到 A="__tombstone__" (NORMAL) → 返回 "__tombstone__" ✅
   （ValueType=NORMAL，所以是普通值，不是删除标记）
```

**场景4：多次更新与删除**
```
时间线：
T1: Put(A=1) → Flush → L0_001.sst (A=1, NORMAL)
T2: Put(A=2) → Flush → L0_002.sst (A=2, NORMAL)
T3: Delete(A) → 写入 Tombstone → Flush → L0_003.sst (A="", TOMBSTONE)
T4: Put(A=3) → 当前在 MemTable (A=3, NORMAL)

查询 Key=A:
1. MemTable: 找到 A=3 (NORMAL) → 返回 3 ✅
```

## 6.6 思考题详解

### 思考题1：如果 Key 在 MemTable 和 SSTable 中都存在，应该返回哪个值？

**答案：返回 MemTable 中的值。**

**原因：**
- MemTable 中的写入发生在 SSTable Flush 之后
- MemTable 代表"最新状态"
- SSTable 是"历史快照"

**代码验证：**
```cpp
// 假设 MemTable 中有 A=4，L0_003.sst 中有 A=3
auto result = kvstore->get("A");
// result = 4（来自 MemTable）
```

### 思考题2：如果 Key 被删除后又重新写入，查询结果应该是什么？

**答案：应该返回重新写入的新值。**

**详细分析：**
```
时间线：
T1: Put(A=1) → Flush → L0_001.sst (A=1)
T2: Delete(A) → 写入 Tombstone → Flush → L0_002.sst (A=__tombstone__)
T3: Put(A=2) → 当前在 MemTable (A=2)

查询 Key=A:
1. MemTable: 找到 A=2 → 返回 2 ✅
   （即使 L0_002 中有 Tombstone，也不会查到，因为 MemTable 优先）
```

**关键理解：**
- MemTable 的优先级高于所有 SSTable
- 只要 MemTable 中有这个 Key（无论是普通值还是 Tombstone），就不再查 SSTable
- 这保证了查询结果的正确性和一致性

## 6.7 读路径优化：Bloom Filter（预告）

**问题：**
- 如果 Key 不在任何 SSTable 中，需要遍历所有 SSTable 才能确定
- 大量无效查询会导致磁盘 I/O 浪费

**解决方案：Bloom Filter（布隆过滤器）**
- 每个 SSTable 配备一个 Bloom Filter
- Bloom Filter 可以快速判断"Key 绝对不在这个 SSTable 中"
- 如果 Bloom Filter 说"不在"，就跳过这个 SSTable
- 如果 Bloom Filter 说"可能在"，再去查 SSTable

**查询流程（带 Bloom Filter）：**
```
用户查询 Key
    ↓
1. 查 MemTable
    ↓
2. 遍历 SSTable（从新到旧）
   - 检查 Bloom Filter
   - 如果 Bloom Filter 说"不在" → 跳过这个 SSTable
   - 如果 Bloom Filter 说"可能在" → 读取 SSTable
    ↓
3. 返回结果
```

**注意：** Bloom Filter 有一定的误判率（假阳性），但不会有假阴性。即：
- 说"不在" → 一定不在
- 说"可能在" → 可能在，也可能不在（需要实际查询确认）
