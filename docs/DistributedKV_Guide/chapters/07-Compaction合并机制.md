# 7. Compaction 合并机制

## 7.1 什么是 Compaction？（用生活类比理解）

### 7.1.1 一个生活中的例子

想象一下你的书桌：

```
场景：你在复习考试，每天都会产生很多笔记

第1天：写了一张笔记纸，放在桌上
第2天：又写了一张，叠在上面
第3天：又写了一张...
...
第30天：桌上堆了30张纸！

问题来了：
1. 找某天的笔记很慢（要一张张翻）
2. 同一个知识点可能写在多张纸上（重复了）
3. 有些纸已经没用了（比如"今天要买牛奶"这种待办事项已完成）
4. 桌子快放不下了
```

**你会怎么做？**

当然是**整理**！把30张纸收起来，去掉重复的，扔掉过期的，装订成一个本子。

这就是 **Compaction** 做的事情——**整理磁盘上的数据文件**。

### 7.1.2 通俗定义 vs 专业定义

| 角度 | 解释 |
|------|------|
| **通俗理解** | Compaction 就是"整理房间"，把散落的文件合并、去重、清理垃圾 |
| **专业定义** | Compaction 是 LSM-Tree 的后台合并机制，将多个 SSTable 文件合并排序，清理过期数据和 Tombstone |

### 7.1.3 为什么需要 Compaction？

**用书桌类比理解问题：**

| 书桌问题 | 对应 LSM-Tree 问题 | 专业术语 |
|----------|-------------------|----------|
| 纸张太多，找东西慢 | SSTable 文件太多，查询要遍历很多文件 | **读取放大** |
| 同一知识点写了好几遍 | 同一个 Key 在多个文件中存在 | **数据冗余** |
| 过期的待办事项占地方 | 删除标记（Tombstone）占用空间 | **空间放大** |
| 桌子快放不下了 | 磁盘空间不足 | **存储效率低** |

**Compaction 的作用：**

```
整理前：30张散落的纸，找一张要翻10秒
整理后：1个装订好的本子，找一张只要1秒

对应到 LSM-Tree：
整理前：10个 SSTable 文件，查询要读10个文件
整理后：1个合并后的 SSTable，查询只需读1个文件
```

## 7.2 LSM-Tree 的分层架构（用楼层类比）

### 7.2.1 用大楼来理解分层

想象一栋大楼，数据从上往下"流动"：

```
┌─────────────────────────────────────────────────────┐
│  🏠 顶层：你的书桌（内存）                            │
│  └─ 最新的数据在这里，随时可以修改                      │
│  └─ 空间有限，放不下了就要搬到楼下                      │
└─────────────────────────────────────────────────────┘
                        ↓ 搬家（Flush）
┌─────────────────────────────────────────────────────┐
│  📦 L0 层：临时存放区                                 │
│  └─ 刚从楼上搬下来的箱子，还没整理                      │
│  └─ 箱子之间可能重叠（同一个东西在多个箱子里）            │
│  └─ 找东西要一个个箱子翻                               │
└─────────────────────────────────────────────────────┘
                        ↓ 整理（Compaction）
┌─────────────────────────────────────────────────────┐
│  📚 L1 层：正规书架                                   │
│  └─ 已经整理好的书，按顺序排列                          │
│  └─ 每本书的位置固定，找起来很快                        │
│  └─ 书架满了就要往更下层搬                             │
└─────────────────────────────────────────────────────┘
                        ↓ 继续整理
┌─────────────────────────────────────────────────────┐
│  📚 L2 层：更大的仓库                                 │
│  └─ 容量是 L1 的 10 倍                                │
│  └─ 同样是有序排列的                                   │
└─────────────────────────────────────────────────────┘
```

### 7.2.2 L0 层为什么"乱"？

**生活类比：**

```
你刚搬家，箱子一个个往新家搬：

第1个箱子：装了 A-E 的书
第2个箱子：装了 C-G 的书（和第1个箱子有重叠！）
第3个箱子：装了 F-J 的书（和第2个箱子有重叠！）

为什么重叠？因为你搬家时没时间整理，直接把书桌上的东西装箱。
书桌上的书本来就是混在一起的。
```

**对应到 LSM-Tree：**

- **L0 层**：直接接收 MemTable Flush 的产物
- **为什么重叠**：每次 Flush 只是"把当前内存里的数据倒出来"，不保证全局有序
- **后果**：查询 L0 时，可能要查多个文件才能找到目标

### 7.2.3 L1 层为什么"整齐"？

**生活类比：**

```
你花了一个周末整理 L0 的箱子：

1. 把所有箱子倒出来
2. 按字母顺序排列
3. 每10本书装一箱，贴上标签（A-J, K-T, U-Z）
4. 放到 L1 书架上

现在找书：
- 找 "M" 开头的书 → 直接去第二个箱子（K-T）
- 不用翻其他箱子！
```

**对应到 LSM-Tree：**

- **L1 层**：经过 Compaction 整理后的文件
- **为什么不重叠**：Compaction 时做了全局排序，确保每个文件的 Key 范围不重叠
- **好处**：查询时可以快速定位到目标文件

### 7.2.4 专业术语总结

| 通俗说法 | 专业术语 | 解释 |
|----------|----------|------|
| 书桌 | MemTable | 内存中的数据结构，最新数据 |
| 搬家 | Flush | 把内存数据写入磁盘 |
| 临时存放区 | L0 层 | Flush 产物的存放位置，文件重叠 |
| 正规书架 | L1+ 层 | Compaction 后的有序文件 |
| 整理 | Compaction | 合并排序，清理垃圾 |

## 7.3 Compaction 怎么做？（用合并作业类比）

### 7.3.1 多路归并排序——用"合并作业"类比

**场景：** 老师让你把4个小组的作业合并成一本，每个小组的作业已经按学号排好序了。

```
小组1: [1号, 3号, 5号, 7号]
小组2: [2号, 4号, 6号, 8号]
小组3: [1号, 5号, 9号]      ← 注意：1号和5号在小组1也有
小组4: [3号, 7号, 11号]     ← 注意：3号和7号在小组1也有

目标：合并成一本，按学号排序，重复的只保留最新的
```

**怎么做最快？**

```
方法1（笨办法）：
- 把所有作业倒在一起
- 重新排序
- 问题：浪费时间和空间

方法2（聪明办法——多路归并）：
- 每个小组派一个代表，拿着当前最小的学号
- 比较所有代表手里的学号，选最小的
- 选中的代表回去拿下一个作业，继续比较
- 重复直到所有作业都处理完
```

**图解过程：**

```
初始状态：
小组1代表: [1号]  小组2代表: [2号]  小组3代表: [1号]  小组4代表: [3号]
           ↓              ↓              ↓              ↓
比较：1号 vs 2号 vs 1号 vs 3号 → 选最小的 1号

问题：有两个 1号，选哪个？
答案：选"最新"的那个（小组3的，因为小组3是后交的作业）

第1步结果：[1号(来自小组3)]

继续：
小组1代表: [1号]  小组2代表: [2号]  小组3代表: [5号]  小组4代表: [3号]
           ↓              ↓              ↓              ↓
比较：1号 vs 2号 vs 5号 vs 3号 → 选最小的 1号（小组1）

第2步结果：[1号(小组3), 1号(小组1)]
但是！同一个学号只保留最新的，所以小组1的1号被丢弃

实际结果：[1号(小组3)]

继续...直到所有作业处理完
```

### 7.3.2 专业术语：多路归并排序

**通俗解释：** 把多个已经排好序的序列，合并成一个有序序列。

**专业定义：** 使用最小堆（Min-Heap）维护多个迭代器的当前最小元素，每次取出堆顶元素，然后将该迭代器前进一位，重新入堆。

**代码示例（简化版）：**

```cpp
// 假设我们有多个已经排好序的列表
// 就像多个小组的作业，每个小组内部已经按学号排序

std::vector<int> group1 = {1, 3, 5, 7};
std::vector<int> group2 = {2, 4, 6, 8};

// 多路归并的过程：
// 1. 比较当前最小的元素
// 2. 取出最小的
// 3. 继续比较

// 结果：[1, 2, 3, 4, 5, 6, 7, 8]
```

### 7.3.3 重复 Key 怎么处理？

**生活类比：**

```
小组1: 小明的作业，第1版
小组2: 小明的作业，第2版（修改过）
小组3: 小明的作业，第3版（又修改过）

合并时：只保留第3版（最新的）
```

**对应到 LSM-Tree：**

```
L0_001.sst: Key=A, Value=1
L0_002.sst: Key=A, Value=2  ← 更新
L0_003.sst: Key=A, Value=3  ← 最新

Compaction 后：只保留 Value=3
```

## 7.4 Tombstone（删除标记）怎么处理？

### 7.4.1 用"作废的文件"类比

**场景：** 你在整理文件柜，发现一份文件上盖了"作废"章。

```
情况1：文件柜里只有这一份文件（盖了"作废"）
→ 你可以把它扔掉

情况2：文件柜里有两份同名文件
   - 旧文件：有效
   - 新文件：盖了"作废"
→ 保留"作废"的那份（因为它代表"这个文件已删除"）

情况3：文件柜里有三份同名文件
   - 最旧：有效
   - 中间：盖了"作废"
   - 最新：有效（又恢复了）
→ 只保留最新的有效文件
```

### 7.4.2 专业解释

**什么是 Tombstone？**

- **通俗理解**：一张写着"已删除"的小纸条
- **专业定义**：一种特殊的标记，表示某个 Key 已被删除

**为什么需要 Tombstone？**

```
问题：SSTable 是不可变的（一旦生成就不能修改）

用户删除 Key=A：
- 不能去 SSTable 里把 A 删掉（SSTable 不能改）
- 只能写一个"Key=A 已删除"的标记
- 查询时，看到这个标记就知道 A 已被删除
```

**Compaction 时如何处理 Tombstone？**

| 情况 | 处理方式 | 原因 |
|------|----------|------|
| Tombstone 是最新版本 | 保留 Tombstone | 告诉查询者"这个 Key 已删除" |
| Tombstone 后面有新值 | 丢弃 Tombstone，保留新值 | 新值覆盖了删除操作 |
| Tombstone 是唯一版本 | 可以丢弃（高级优化） | 没人关心这个 Key 了 |

## 7.5 Compaction 什么时候触发？

### 7.5.1 用"房间太乱"类比

```
触发整理的条件：

条件1：箱子太多
- L0 层文件数量 ≥ 4 个
- 就像房间里箱子堆不下了

条件2：书架太满
- L1 层大小超过限制
- 就像书架放不下了
```

### 7.5.2 触发时机

| 方式 | 通俗解释 | 优缺点 |
|------|----------|--------|
| **同步触发** | 每次搬家后立刻整理 | 简单，但可能阻塞后续搬家 |
| **异步触发** | 后台自动整理，不影响你继续往书桌放东西 | 复杂，但体验更好 |

**本项目第一阶段：** 采用同步触发（简单实现）

## 7.6 Compaction 对系统的影响

### 7.6.1 用"整理房间的代价"类比

| 整理的代价 | 对应 LSM-Tree 的代价 | 专业术语 |
|------------|---------------------|----------|
| 整理时要搬来搬去，比直接扔东西累 | 写入数据时实际写的比用户写的多 | **写入放大** |
| 整理期间房间更乱 | 整理期间占用额外空间 | **空间放大** |
| 找东西要翻更多地方 | 查询要读更多文件 | **读取放大** |

### 7.6.2 专业解释

**写入放大（Write Amplification）：**

```
用户写入 1MB 数据：
- Flush 写入 1MB
- L0→L1 Compaction 又写了 1MB
- L1→L2 Compaction 又写了 1MB
- ...

实际写入磁盘：可能 10MB 甚至更多
写入放大 = 10MB / 1MB = 10x
```

**空间放大（Space Amplification）：**

```
用户数据：100MB
实际占用：150MB（因为有多版本数据、Tombstone 等）
空间放大 = 150MB / 100MB = 1.5x
```

**读取放大（Read Amplification）：**

```
查询一个 Key：
- 查 MemTable：1 次
- 查 L0（4个文件）：4 次
- 查 L1：1 次
总共：6 次读取
读取放大 = 6
```

## 7.7 Compaction 实现要点

### 7.7.1 文件管理的原子性

**用"搬家不能丢东西"类比：**

```
错误的搬家方式：
1. 把旧家的东西扔掉
2. 搬到新家
3. 搬运车半路翻了 → 东西全没了！

正确的搬家方式：
1. 先把东西搬到新家
2. 确认新家东西齐全
3. 再清理旧家
4. 如果搬运出问题，旧家还有备份
```

**对应到 Compaction：**

```
错误方式：
1. 删除旧的 SSTable
2. 生成新的 SSTable
3. 生成失败 → 数据丢失！

正确方式：
1. 生成新的 SSTable（用临时文件名）
2. 确认生成成功
3. 原子性地重命名为正式文件名
4. 删除旧的 SSTable
```

### 7.7.2 内存管理

**用"不能一次搬太多"类比：**

```
错误方式：
- 把所有箱子一次搬完
- 结果：搬不动，累趴下

正确方式：
- 一次搬一个箱子
- 搬完再搬下一个
```

**对应到 Compaction：**

```
错误方式：
- 把所有 SSTable 一次加载到内存
- 结果：内存溢出

正确方式：
- 使用迭代器，按需读取
- 流式处理，不一次性加载所有数据
```

## 7.8 本项目的实现计划

### 7.8.1 第一阶段（第 6 周）：简单 Compaction

**目标：** 实现 L0 → L1 的基本合并

**简化点：**
- 只处理 L0 层（不管 L1→L2）
- 同步触发（每次 Flush 后检查）
- 简单的 Tombstone 处理（保留，不丢弃）

**不包含：**
- 多层 Compaction
- 后台异步执行
- 快照支持

### 7.8.2 后续优化方向

- 多层 Leveled Compaction
- 后台异步 Compaction
- Compaction 暂停/恢复
- 更智能的 Tombstone 清理

## 7.9 思考题（带答案）

### 思考题 1：为什么 L0 层文件会重叠，而 L1 层不会？

**通俗答案：**
- L0 就像刚搬家的箱子，还没整理，东西乱放
- L1 是整理后的书架，每本书都有固定位置

**专业答案：**
- L0 直接接收 MemTable Flush，每次 Flush 只保证单个文件内部有序
- L1 经过 Compaction 合并排序，确保文件间 Key 范围不重叠

### 思考题 2：Compaction 会影响正在进行的查询吗？

**通俗答案：**
- 不会。就像你在整理房间时，别人可以继续看书架上已有的书
- 整理完成后，新书架"替换"旧书架，新查询会看到整理后的结果

**专业答案：**
- Compaction 生成新文件后，原子性地更新文件列表
- 查询过程中使用的是旧的文件列表
- 新的查询会看到合并后的结果

### 思考题 3：如何判断一个 Tombstone 可以被清理？

**通俗答案：**
- 这个"作废"标记是最新的
- 没有人在用旧的文件（没有快照引用）
- 已经覆盖了所有可能的地方

**专业答案：**
1. 该 Tombstone 是该 Key 的最新版本
2. 没有活跃的快照引用旧数据
3. Tombstone 已经覆盖了所有下层的数据
